# DONGJIN 第三阶段开发任务：系统收官、错误产生与在线错误研判

## 1. 第三阶段的定位

第三阶段不在后台自动生成训练数据、训练模型或切换模型，而是在前两阶段基础上
把这些能力整理为用户可显式执行的命令/API，并完成在线研判闭环：

```text
第一阶段
SimBench + pandapower → P1权威电网包 → Neo4j静态拓扑 → Redis动态潮流

第二阶段
P1权威电网包 → 离线场景 → Truth → Measurement → GNN数据集 → 合格候选模型

用户执行明确命令生成数据并训练模型
        ↓
用户执行明确命令选择推理模型，系统检查兼容性
        ↓
Redis当前动态快照 → 在线MeasurementFrame → 统一特征 → GNN推理
        ↓
异常检测 → 故障分类 → 位置定位 → 影响分析 → 上下游溯源 → 白箱报告
```

第三阶段完成后，项目才形成可实际演示和持续扩展的完整应用：

1. 用户启动标准电网和连续潮流。
2. 系统持续从Redis读取当前动态快照。
3. 用户指定的模型消费与训练时完全一致的48维特征。
4. 检测到异常时输出类型、位置、置信度、候选列表、影响范围和溯源路径。
5. 测试/演示模式可以在隔离影子环境中产生已知错误，验证模型是否盲判正确。
6. 正常在线模式不主动制造错误，只研判实际进入系统的数据。
7. 每次输入、特征、模型输出、规则修正和最终结论都有可见文件记录。

本阶段是项目最后一个开发阶段，不再预留“第四阶段”承接必要功能。凡是完成本项目
正常使用、训练、测试、错误产生、在线研判和维护所必需的能力，都必须在本阶段
实现、验收或形成明确的手动命令。无法由本项目单独提供的真实生产数据、硬件设备
和真实电网控制权，只作为最终系统边界写入文档，不描述成待开发阶段。

## 2. 当前基础与必须先解决的问题

### 2.1 已有基础

- P1权威电网包已生成并版本化。
- Neo4j已具备静态拓扑投影接口。
- Redis/Memurai已具备当前动态潮流快照接口。
- 第二阶段已生成108个场景和94,176行白箱训练数据。
- `p1-v1-gcn-model-v3`已通过当前离线严格门槛。
- Java已有`PythonComputeGateway`和错误研判服务骨架。
- 前端已有拓扑显示和错误研判展示区域。

### 2.2 当前不能直接接入v3的原因

当前存在明确的训练—在线偏差：

| 项目 | 第二阶段标准模型 | 当前旧在线盲判 |
|---|---|---|
| 特征数量 | 48维 | 8维 |
| 数据来源 | pandapower Truth转换出的Measurement | 前端随机构造 |
| 图身份 | P1稳定businessId | 前端当前节点/边ID |
| 缺失处理 | 显式missing mask | 无统一契约 |
| 质量码 | GOOD/SUSPECT/BAD/MISSING/FROZEN | 无 |
| 归一化 | 冻结的训练集参数 | 旧StandardScaler |
| 模型文件 | `artifacts/models/.../model.joblib` | 根目录旧active-model |
| 拓扑签名 | 完整SHA-256 | 旧短签名 |

因此第三阶段不能只把v3文件改名后交给旧接口。必须先建立统一在线特征适配器，
用模型目录中的`feature-schema.json`和`normalization.json`处理在线输入。

是否继续扩充数据、何时训练、使用哪个模型以及何时重新测试，全部由用户通过
项目提供的明确命令/API/按钮决定；任何其他流程都不能隐式触发这些动作。

## 3. “产生错误”的几种解决方案

“产生错误”必须区分使用目的。训练造错、盲测造错和真实运行故障不是同一件事。

### 3.1 方案A：pandapower影子电网物理事件注入

做法：

1. 从P1 `network.json`创建独立副本。
2. 复制当前SimBench曲线时刻。
3. 在副本中修改线路、变压器、开关、负荷或电源状态。
4. 重新执行`runpp()`。
5. 把计算结果转换为与在线快照相同的MeasurementFrame。

适合产生：

- 线路停运；
- 变压器停运；
- 开关误分/误合；
- 负荷突增；
- 分布式电源出力骤降；
- 由上述事件真实计算得到的过载、欠压、孤岛或供电中断。

优点：

- 电流、电压、功率和负载率之间保持物理一致。
- 能保留基线与事件后的完整对照。
- 与第二阶段数据生成逻辑一致。
- 可以精确知道根因和影响范围。

缺点：

- 依赖潮流收敛。
- 稳态潮流不能完整表达毫秒级电磁暂态和继电保护动作。
- 不应在正式在线pandapower实例上直接修改。

结论：这是物理故障的首选方案。

### 3.2 方案B：量测层异常注入

做法：

1. 保留pandapower物理真值不变。
2. 在Truth到Measurement的转换层施加异常。
3. 记录原值、变换、输出值、时间戳和质量码。

适合产生：

- 固定偏置；
- 漂移；
- 丢失；
- 冻结；
- 延迟；
- 乱序；
- 量化；
- 单位/变比配置错误；
- 噪声突然增大。

优点：

- 能严格区分“电网真的坏了”和“传感器/数据链路坏了”。
- 不破坏P1或物理真值。
- 速度快，适合批量生成。

缺点：

- 不能代替线路、变压器等真实物理故障。
- 必须保证模型标签把物理根因和量测异常分开。

结论：这是传感器和数据质量错误的首选方案，应与方案A组合使用。

### 3.3 方案C：已归档场景重放

做法：

- 从`artifacts/scenarios`读取指定场景；
- 按原随机种子重新计算，或直接重放已冻结MeasurementFrame；
- 将同一输入重复提交给模型；
- 对比新旧模型输出。

优点：

- 完全可复现。
- 适合回归测试、模型版本对比和产品演示。
- 不依赖每次随机采样是否刚好命中某类故障。

缺点：

- 只能覆盖已经归档的场景。
- 不能单独承担新数据扩充。

结论：这是验收和回归的必备方案。

### 3.4 方案D：在线影子会话

做法：

```text
正常在线分支
Redis: dongjin:snapshot:active
         ↓ 只读复制当前状态
影子会话
pandapower独立副本 + 物理/量测事件
         ↓
Redis: dongjin:shadow:{sessionId}:snapshot:active
         ↓
模型盲判
```

影子会话拥有独立：

- `sessionId`；
- pandapower网络副本；
- 仿真时钟；
- Redis Key命名空间和TTL；
- 错误真值档案；
- 推理结果档案。

优点：

- 用户可以在在线系统运行时按按钮创建测试故障。
- 不污染正式Redis活动快照和Neo4j拓扑。
- 可以完整演示“产生错误—模型发现—揭示答案”的流程。

缺点：

- 实现复杂度高于单纯离线场景。
- 必须防止影子Key被正常页面当成正式快照。

结论：这是第三阶段交互演示的推荐方案。

### 3.5 方案E：真实历史数据或硬件仿真

来源可以是合法脱敏SCADA/PMU历史、数字实时仿真器或硬件在环系统。

优点：

- 更接近真实生产分布。
- 可以验证SimBench模拟数据与真实数据之间的差距。

缺点：

- 当前项目没有这些数据源和设备。
- 涉及数据授权、隐私、字段映射和安全审查。
- 不能为了“像真的”而伪称拥有真实历史数据。

结论：本项目提供可扩展的数据映射接口、导入校验和操作文档；是否接入真实来源取决于
用户今后能否取得合法数据或设备授权，不作为另一个待开发阶段，也不影响本项目收官。

### 3.6 推荐组合

第三阶段采用：

| 使用场景 | 推荐方式 |
|---|---|
| 用户手动扩充训练数据时 | 可选使用A物理事件 + B量测异常 + C场景重放导出的白箱文件 |
| 自动化回归 | C固定场景重放 |
| 前端盲测演示 | D在线影子会话，内部组合A/B |
| 正常正式运行 | 不造错，只读取正式Redis快照并研判 |
| 获得授权后的外部验证 | E真实历史/硬件仿真，经用户显式导入 |

不再使用的方式：

- 前端直接随机填写电压、电流和功率；
- 前端按固定比例向邻居传播“异常数值”；
- 直接修改pandapower结果表；
- 把测试故障写入正式`dongjin:snapshot:active`；
- 修改Neo4j活动拓扑来假装线路故障。

## 5. 第三阶段范围

### 5.1 包含

- 造数、训练、评估、模型选择、手动回滚、造错、短路分析和研判的独立命令/API；
- 训练和在线共用的FeatureFrame契约。
- Redis快照到48维标准特征的适配。
- 前端每秒读取并展示一次完整的“当前快照”，不把不同时间帧拼接在一起。
- 物理故障、量测异常和场景重放。
- 使用pandapower短路模块的独立短路分析入口、Schema、报告和前端结果展示。
- 独立影子会话及隔离Redis Key。
- 用户手动指定一个模型目录。
- 当前模型选择历史和用户显式触发的手动回滚。
- 模型文件、P1、图签名、特征Schema和归一化参数的最低兼容检查。
- 在线推理、异常阈值、Top-K位置和类别输出。
- Neo4j拓扑辅助的上下游溯源和影响分析。
- 规则校核与模型结果的明确分层。
- 研判输入、输出和中间数据白箱档案。
- 前端正常监控与影子盲测两种模式。
- 自动化测试、端到端测试和性能验收。
- 最终操作手册、数据字典、错误产生手册、模型手册、故障排查和系统边界文档。
- 对旧8维推理、前端随机造错、无用参数、重复接口和冗余代码的最终清理。

### 5.2 最终系统边界（不是第四阶段待办）

以下内容不是被遗漏的开发任务，而是本项目完成后的明确边界：

#### 5.2.1 外部授权和资源边界

- 不接入用户尚未获得授权的真实SCADA、PMU或生产调度数据。
- 不声称SimBench/pandapower模拟结果已经等同真实生产现场验证。
- 没有外部数据或硬件时，项目只提供映射模板、校验入口和接入说明，不能伪造来源。

#### 5.2.2 诊断系统安全边界

- 系统只给出研判、影响范围和建议，不自动执行真实开关操作或调度控制。
- 不自动隔离故障、切除负荷或恢复供电；这些生产动作必须由具备权限的人员和系统完成。
- 普通监控页面不会因为发现异常而自动造数、训练、换模型或控制电网。

#### 5.2.3 物理模型边界

- 稳态潮流用于秒级状态展示，不能冒充毫秒级电磁暂态或继电保护动作过程。
- 短路分析在本阶段实现为独立的手动分析分支；其结果不伪装成连续潮流快照。
- 继电保护定值整定、保护配合和毫秒级动作时序不属于当前稳态数字电网模型的能力，
  最终文档必须说明原因、数据缺口和可对接的外部专业工具。

#### 5.2.4 架构规模边界

- 当前目标是本机单电网、秒级快照和可审计研判，不为没有实际负载需求的场景引入
  Kafka、分布式流处理或集群训练。
- 若未来部署规模发生变化，应依据实测吞吐量重新选型；这不是当前项目未完成项。

#### 5.2.5 自动化边界

- 系统实现造数、训练、评估、模型选择、手动回滚、造错和研判能力，但每项都由用户
  用独立命令/API/按钮明确触发。
- 不未经用户命令生成所谓“最终训练数据集”，不自动训练、挑选或替换模型。
- 不建设自动发布、自动激活和自动回滚状态机；保留可审计的选择历史，并提供用户
  显式执行的回滚命令。

### 5.3 统一手动操作原则

本文中的“手动”不是让用户修改Python源码、自己拼JSON或逐文件处理，而是：

> 用户执行一条明确命令、调用一个明确API或按下一个明确按钮；随后系统在该命令
> 授权的范围内自动完成校验、计算、保存和报告，但不会继续触发其他未授权流程。

例如，用户执行一次训练命令后，程序可以自动完成数据读取、训练、验证、保存模型
和输出指标；但训练完成后不能自动选择该模型用于在线推理。

所有改变系统状态的操作必须遵守：

1. 必须有明确的用户触发入口。
2. 命令执行前显示输入对象、配置和目标版本。
3. 命令执行后返回任务ID、状态和白箱产物路径。
4. 失败时保留失败原因，不悄悄切换到其他数据或模型。
5. 长时任务提供`status`和`stop`命令。
6. 命令、Java API和前端按钮复用同一服务逻辑，不实现三套业务。
7. 查询和页面刷新可以自动进行，但不得因此产生新场景、训练模型或切换模型。

已存在的手动入口：

| 操作 | 手动入口 | 状态 |
|---|---|---|
| 启动Memurai | `.\scripts\start-memurai.ps1` | 已存在 |
| 查看Memurai | `.\scripts\status-memurai.ps1` | 已存在 |
| 停止Memurai | `.\scripts\stop-memurai.ps1` | 已存在 |
| 启动Python服务 | `python -m uvicorn app.main:app --host 127.0.0.1 --port 8001` | 已存在 |
| 完整离线造数并训练 | `python scripts\run_offline_training_pipeline.py ...` | 已存在 |
| 生成/发布P1 | Java API或前端按钮 | 已存在 |
| 启动/暂停/继续/停止潮流 | Java API或前端按钮 | 已存在 |

第三阶段需要新增的手动入口：

| 操作 | 计划命令 |

## 6. 核心数据契约

### 6.1 `grid-feature-frame-v2`

训练与在线推理必须共同读取同一契约：

| 字段 | 含义 |
|---|---|
| `frameId` | 特征帧唯一ID |
| `sourceFrameId` | 来源Redis快照或离线MeasurementFrame |
| `sourceMode` | `ONLINE`、`SHADOW`或`REPLAY` |
| `gridId` | P1电网身份 |
| `topologyVersion` | 拓扑版本 |
| `graphSignature` | 图签名 |
| `featureSchemaVersion` | 48维特征Schema |
| `normalizationVersion` | 归一化参数版本 |
| `simulationTime` | 仿真时间 |
| `generatedAt` | 特征生成时间 |
| `vertices` | 按稳定businessId排序的完整顶点特征 |

每个顶点必须包含：

- `businessId`；
- `elementType`；
- 48个特征；
- 缺失掩码；
- 质量码；
- 原始字段来源；
- 是否经过补齐或转换。

### 6.2 `manual-model-contract-v1`

第三阶段不自动发布或选择模型。用户通过命令明确选择一个模型，例如：

```powershell
python scripts\select_inference_model.py --model-id p1-v1-gcn-model-v3
```

命令完成兼容检查后，原子更新`config/inference-model.json`，并在
`artifacts/model-selection-history/`追加一条不可覆盖的选择记录。环境变量
`DONGJIN_INFERENCE_MODEL_DIR`只作为高级覆盖方式，不要求普通使用者手工编辑。

该目录至少必须包含：

```text
model.joblib
manifest.json
feature-schema.json
label-schema.json
normalization.json
```

服务加载前只做运行必需的兼容检查。模型Manifest至少需要提供：

- `modelId`；
- `datasetId`；
- P1 `gridId/topologyVersion`；
- `graphSignature`；
- Feature/Label/Normalization Schema；
- 代码版本和依赖版本；
- 训练配置和随机种子（由用户训练流程提供，服务只展示）；
- 验证/测试指标（若存在则展示，不由第三阶段重新计算）；
- 异常阈值；
- 模型文件SHA-256。

更换模型由用户再次执行选择命令并明确重载或重启服务完成。回滚同样是用户显式执行，
其含义只是把配置恢复到上一条已通过兼容检查的人工选择记录。第三阶段不自动选择模型、
不判断哪个模型“最终最好”，也不建立自动发布、自动激活、自动退役或自动回滚状态机。

## 12. 模块 T5：错误研判、影响分析与解释

**目标**：在模型原始输出之上形成用户可理解的电网错误结论。

### 12.1 模型与规则的边界

必须分别显示：

- **模型判断**：最可能的错误类型、位置和概率。
- **规则事实**：电压是否越限、线路是否过载、开关是否断开、数据是否缺失。
- **拓扑推导**：上下游路径、受影响负荷和供电边界。
- **最终结论**：综合模型、规则和拓扑后的研判摘要。

规则不能偷偷修改模型概率；若规则否决或修正模型，必须记录：

```text
原始模型结果
→ 触发的规则
→ 修正原因
→ 最终结果
```

### 12.2 任务

| 编号 | 任务 | 验收标准 |

| T5.1 | 异常事实提取 | 电压、负载率、连通性、缺失和质量码事实可见 |
| T5.2 | 位置校核 | 模型目标必须属于当前活动P1拓扑 |
| T5.3 | 类型校核 | 线路、变压器、开关和量测异常类型与目标兼容 |
| T5.4 | 上游溯源 | 沿Neo4j标准关系追踪电源侧路径 |

| T5.6 | 环网处理 | 使用访问集合和方向规则避免循环 |
| T5.7 | 候选比较 | Top-K候选的证据、分数和规则事实可比较 |
| T5.8 | 置信度分级 | 高/中/低置信度门槛明确 |
| T5.9 | 数据不足 | 无法研判时返回原因，不伪造结论 |

## 19. 第三阶段完成后的系统状态

第三阶段完成后，核心组件和操作层的职责最终固定为：

```text
Neo4j
  保存并查询当前P1静态拓扑、设备参数和上下游关系

pandapower
  计算正常在线潮流；在独立影子副本中计算测试物理错误

Redis/Memurai
  保存正式当前动态快照；供前端每秒读取；使用隔离命名空间保存短期影子快照

GNN + 研判服务
  消费标准FeatureFrame，完成异常检测、分类、定位、影响和解释

手动操作层（CLI / 独立管理接口 / 按钮）
  显式启动造数、训练、评估、模型选择/回滚、造错、短路分析和研判
```

真实应用运行时不会主动产生错误。只有用户进入影子盲测模式或执行离线训练时，
系统才会模拟错误；正常在线模式只观察和研判正式数据。页面所说的“每秒快照”
就是每秒读取一个完整时刻的数据画面，不代表把每一秒的数据永久复制保存。所有
会改变数据、模型或运行状态的操作均由用户显式触发，最终手册提供完整执行方法。
